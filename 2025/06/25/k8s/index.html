Components

K8s存在控制面和Node的概念,他们都利用CRI支持的ContainerRuntime运行必要的容器以支持集群的运行

podLifeCycle

https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#container-states

当我们在创建pod时,pod会经历如下阶段

Pending

Pod的创建请求被系统接受,但POD中的容器未有一个运行起来 比如拉取镜像,调度节点都是这个状态

Running

Pod中的容器至少运行一个,便会由Pending转换为Runing

init

配置了初始化容器的POD会在此处等待init命令执行

Succeed

Pod完成了自己的任务

Failed

异常的失败 通常是配置错误

unknow

通常是无法与POD通信

RestartPolicy

在POD中容器第一次启动失败后,POD层面都配有restartPolicy来定时重启失败的容器

containerLifeCycle

Waiting

等待状态,镜像或者Secret等

Running

运行状态

Terminate

终结状态,容器所在的POD被执行delete,正等待容器服务停止

优雅关闭

首先,我们知道Linux中任务管理,停止一个进程可以kill -9(SIGKILL),-15(SIGTERM),-3(SIGQUIT),其中SIGKILL就是强制终止,而SIGTERM(默认)会等待进程所有任务结束后关闭

当我们对一个POD kubectl delete时不带force就会触发优雅关闭;为什么需要?当一个Tomcat对外提供服务时,直接删除可能直接导致用户连接的丢失;所以默认会对一个POD有一个宽限期(30S),让他有时间处理自身的业务并拒绝后面的连接,30S后无论处理完否,直接删除

好吧,来一个简陋的说明,这个napPOD的业务就是sleep 9000

我们来删除他,就会触发Terminate他会等待业务结束(sleep 9000)后删除;但会因为terminationGracePeriodSeconds强制在30S后删除

但是,某些容器不会等待这个时间

可以使用podHook 他提供两个参数postStart和preStop分别在POD创建后和停止前并行执行

指定使用kubectl delete时,先等待30S,然后再使用nginx -s quit优雅退出

主要通过pod.spec.containers.resources下的limits和requests来限制POD资源的使用

resourcesLimit

创建一个资源限制POD;CPU和内存资源的计算方式,简单来说内存尽量Mi,Gi等单位,CPU 1000M == 1CPU Core,500M == 0.5CPU Core;即可以写0.5,也可以写500M,推荐后者

LimitRange

为了避免POD无限制使用宿主机资源,导致其他POD资源紧张,甚至致使宿主机宕机,我们需要给POD设置资源申领的限制

一个 LimitRange（限制范围） 对象提供的限制能够做到：

  • 在一个命名空间中实施对每个 Pod 或 Container 最小和最大的资源使用量的限制。
  • 在一个命名空间中实施对每个 PersistentVolumeClaim 能申请的最小和最大的存储空间大小的限制。
  • 在一个命名空间中实施对一种资源的申请值和限制值的比值的控制。
  • 设置一个命名空间中对计算资源的默认申请/限制值，并且自动的在运行时注入到多个 Container 中。

Cordon/Drain/Taint

Taint的设置格式

key:value=effect

  • key: 键值对的键
  • value: 键值对的值
  • effect: 影响值

我们着重看这个effect他有三个值NoSchedule,NoExecute,PreferNoSchedule

  • NoSchedule: 后续不会将不能Toleration该Node Taints的POD调度到该节点,已存在的POD不受影响
  • NoExecute: 只会影响已经在该节点运行的POD,不满足Toleration条件直接Evicted;满足条件的继续运行;满足条件但设置tolerationSeconds的,在时间结束后Evicted
  • PreferNoSchedule: 理论上不满足Tolerations的不会被调度到该Node

集群认证

先来查看一下kube-apiserver的启动参数

我来尝试总结一下K8s TLS双向验证原理

  1. kubectl的kubeconfig 记录了server-address 向kube-apiserver发起连接
  2. kube-apiserver 提供由 kubeadm生成的服务器证书和数字签名
  3. kubectl使用kubeconfigcertificate-authority-data字段记录了的根CA公钥去验证服务器证书的数字签名 验证了api-server的身份 并还原出一个由服务器证书计算出的HASH1 然后kubectl对服务器证书也计算得出HASH2 HASH1 == HASH2 则单向TLS建立完成
  4. kubectl使用client-certificate-data得出一个HASH3 并使用client-key-data加密HASH3得出数字签名,然后将客户端证书和数字签名发给api-server 当然其中也包括了kubectl的公钥
  5. api-server使用kubectl的公钥解密数字签名,验证了kubectl的身份和HASH3,然后对kubectl证书哈希得出HASH4 HASH3 == HASH4 双向TLS建立完成

沙箱运行容器gVisor

什么是gVisor

在该集群中我选择使用的CRI容器运行时是CRI-O，CRI-O默认的容器运行时处理程序为crun

而这个gVisor(runsc)是谷歌开发的另一种容器运行时处理程序 他和runc crun kata 属于同一个概念

gVisor 是 Google 开源的一个用户态容器运行时,它提供了一个额外的软件层来增强容器的隔离和安全性。

尽管这些容器运行时都属于同一个概念范畴,但它们在实现方式和特性上存在一些差异:

  • gVisor 提供了软件级别的沙箱隔离,介于 runc/crun 和 Kata Containers 之间。
  • runc 和 crun 是轻量级的 OCI 容器运行时,主要负责容器的基本生命周期管理。
  • Kata Containers 则使用了虚拟机技术,提供了更强的隔离性,但开销也更大。

ImagePolicyWebhook容器镜像扫描

这是什么

ImagePolicyWebhook 是 Kubernetes 中用于镜像安全控制的一种准入控制器(Admission Controller)。它允许您在 Kubernetes 集群中部署应用程序时,对镜像进行动态的安全审核和验证。

ImagePolicyWebhook 的工作原理如下:

流程就是kubelet请求到apiserver再被admission拦截 进行检测后 再由admission发送给apiserver

  1. kubelet 发起请求
    • 当 kubelet 需要执行某些操作(如创建 Pod)时,它会向 kube-apiserver 发起 API 请求。
  2. 请求到达 kube-apiserver
    • kube-apiserver 作为 Kubernetes API 的入口点,首先接收来自 kubelet 的请求。
  3. AdmissionController 拦截
    • kube-apiserver 在处理请求之前,会先触发 AdmissionController 插件链。
    • AdmissionController 会对请求进行各种校验和修改,确保请求符合集群的安全和合规性要求。
  4. AdmissionController 检测和处理
    • AdmissionController 会根据预先配置的规则,对 kubelet 发起的请求进行检查和处理。
    • 例如,它可能会验证 kubelet 的身份认证信息,或者修改 Pod 规约中的镜像信息。
  5. 请求发送回 kube-apiserver
    • 如果请求通过了 AdmissionController 的检查,AdmissionController 会将处理后的请求再次发送给 kube-apiserver。
  6. kube-apiserver 处理请求
    • kube-apiserver 收到经过 AdmissionController 处理的请求后,会执行实际的资源创建或更新操作。
    • 例如,对于创建 Pod 的请求,kube-apiserver 会将 Pod 信息下发给对应的 kubelet 节点。
